Teabag QC

Few-shot anomaly detection with DINOv2, Qdrant and a robot arm: a programmer’s tour.

This guide explains what the project does, how every function works, why it is written that way, and which Python features carry the weight. It is pitched at someone who can code but has not met embeddings or vector databases yet. By the end you should be able to rebuild it for your own objects.

The idea

You want to reject bad teabags, but you have no photos of bad ones, and bad can mean torn, stained, crushed or the wrong brand. The trick is to learn what good looks like and flag anything that does not match. This is one-class anomaly detection. It is “few-shot” because 30 to 50 photos are enough.

Embeddings in one paragraph

An embedding model turns an image into a list of numbers (a vector, 768 of them here). Similar-looking images get vectors that point in similar directions, so “how alike are these two images?” becomes a maths question. Cosine similarity measures the angle between vectors: 1.0 means the same direction, lower means less alike.

The algorithm

  1. Enrol: embed good teabags and store the vectors.
  2. Query: embed a new teabag and find its K nearest good neighbours.
  3. Score: anomaly score = 1 − average similarity to those neighbours.
  4. Decide: a score above a threshold means bad. The threshold comes from good bags you held back.
Why one-class? The set of ways a teabag can be wrong is endless and you will never photograph all of them. The set of ways it can be right is small and you control it.

RoleWhereJob

Why split it like this? The Pi is too weak for a vision model, and a camera on the arm would see a different view each time. Keeping the camera fixed and the thinking on the laptop makes every photo comparable and leaves the Pi with one simple job.

Files and the life of one teabag

teabag/
├── pyproject.toml          # dependencies + `teabag-qc` command
├── src/teabag/main.py      # laptop: camera, embeddings, Qdrant, CLI
├── pi/pi_arm_server.py     # copy to the Pi
├── samples/                # cropped photos of enrolled bags (runtime)
└── threshold.json          # decision threshold (runtime)

Pressing Enter on a bag in run triggers this chain:

  1. look() grabs a frame and crops it to the region of interest (ROI).
  2. embed() turns the crop into a vector.
  3. ask_qdrant() finds the nearest good vectors and returns a score.
  4. sort() compares the score with the threshold.
  5. arm_command() sends good or bad to the Pi.
  6. The Pi picks the bag and drops it in the right bin.
Three verbs. look(), ask_qdrant() and sort() are the whole public story. enroll and score reuse the first two, which is why the file stays small.

Config and file layout

main.py reads top to bottom: config, embedding, Qdrant, the three verbs, the arm, the commands, then main(). Each section only uses things defined above it.

CAMERA_INDEX = 0
ROI = (400, 200, 400, 400)            # x, y, w, h
COLLECTION = "teabags"
MODEL_NAME = "facebook/dinov2-small"
K = 3
THRESHOLD_MARGIN = 1.15
THRESHOLD_FILE = Path("threshold.json")
DRY_RUN = True
client = QdrantClient(url="http://localhost:6333")

What each knob does

  • ROI: the crop box. Wrong ROI is the most common cause of poor results, because defects shrink as the bag shrinks in the frame.
  • K: how many neighbours are averaged. One neighbour is noisy; three smooths it out.
  • THRESHOLD_MARGIN: head-room over the worst held-out good score.
  • DRY_RUN: print arm commands instead of sending them.
Why constants at the top? Everything you will tune sits in one place, and nothing is buried in a function. client is created once at module level so every function shares one connection.
Python: Path("threshold.json") is an object, not a string. You get .write_text(), .read_text() and the / operator for joining paths.

embed(): image to vector

@torch.no_grad()
def embed(img: Image.Image) -> list[float]:
    processor, model = _load_model()
    img = img.convert("RGB").resize((224, 224))
    inputs = processor(images=img, return_tensors="pt",
                       do_resize=False, do_center_crop=False).to(_device)
    tokens = model(**inputs).last_hidden_state
    vec = torch.cat([tokens[:, 0], tokens[:, 1:].mean(dim=1)], dim=-1)
    vec = torch.nn.functional.normalize(vec, dim=-1)
    return vec[0].cpu().tolist()

Line by line

  • Resize ourselves. The default processor resizes then centre-crops, which can slice off the edges of the bag. We resize to a square and switch the crop off. The processor then only normalises colours.
  • last_hidden_state holds one vector per image patch (256 of them at 224 px with 14 px patches) plus a CLS token at index 0 that summarises the whole image.
  • CLS + mean patch. We join the global summary (tokens[:, 0]) with the average of all patches (tokens[:, 1:].mean(dim=1)). That gives 384 + 384 = 768 numbers for the small model.
  • Normalise to length 1, so cosine similarity is a plain dot product.
  • .cpu().tolist() turns a GPU tensor into plain Python floats, which Qdrant’s client accepts.
Why DINOv2, not CLIP? DINOv2 is trained to represent visual structure and texture, which is what stains and tears are. CLIP is tuned toward what an image means in words. Swapping is a few lines (page 15).
Python: @torch.no_grad() is a decorator. It switches off gradient tracking, which saves memory and time because we are only running the model, not training it.

Lazy model loading

_device = "cuda" if torch.cuda.is_available() else "cpu"
_processor = _model = None

def _load_model():
    global _processor, _model
    if _model is None:
        _processor = AutoImageProcessor.from_pretrained(MODEL_NAME)
        _model = AutoModel.from_pretrained(MODEL_NAME).to(_device).eval()
    return _processor, _model

def vector_size() -> int:
    _, model = _load_model()
    return model.config.hidden_size * 2

How it works

The model is a module-level variable that starts as None. The first call loads it and every later call reuses it. .to(_device) moves the weights to the GPU if there is one. .eval() puts the model in inference mode, which turns off training-only behaviour such as dropout.

vector_size() asks the model how big its output is (hidden_size doubled, because we join two vectors). The Qdrant collection is created with that number, so changing MODEL_NAME adjusts the size automatically.

Why lazy? Loading the weights takes seconds. With lazy loading, preview opens instantly because it never touches the model. A class would also work, but a global plus a None check is less code for a one-file tool.
Python: assigning to a module variable inside a function needs global, otherwise Python creates a new local variable. _processor = _model = None is chained assignment, and the leading underscore marks the names as private by convention.
Gotcha. If you change the model, the stored vectors have a different size and Qdrant will reject them. Delete the collection and re-enrol.

Qdrant: the memory

def ensure_collection():
    if not client.collection_exists(COLLECTION):
        client.create_collection(COLLECTION,
            vectors_config=models.VectorParams(size=vector_size(),
                                               distance=models.Distance.COSINE))
        client.create_payload_index(COLLECTION, "label",
                                    models.PayloadSchemaType.KEYWORD)

def add_sample(img, label):
    pid = str(uuid.uuid4())
    path = SAMPLES_DIR / f"{label}_{pid[:8]}.jpg"
    img.save(path)
    client.upsert(COLLECTION, points=[models.PointStruct(
        id=pid, vector=embed(img),
        payload={"label": label, "path": str(path), "ts": time.time()})])

Vocabulary

  • Collection: a table of vectors, all the same size.
  • Point: one row: an ID, a vector and a payload (a free-form dictionary).
  • Payload index: makes filtering on label fast.

What the functions do

ensure_collection() is safe to call every time, because it only creates the collection if it does not exist. add_sample() saves the crop to disk, embeds it, and stores the vector with the label, file path and timestamp in one upsert (insert-or-update).

Why store the path? When a bag is rejected, the payload of its nearest neighbours lets you show a reference photo. A UUID as the ID avoids collisions without needing a counter.
Python: SAMPLES_DIR / f"..." uses operator overloading on Path, and pid[:8] slices the first eight characters for a short filename.

ask_qdrant(): the score

def _label_filter(label):
    return models.Filter(must=[models.FieldCondition(
        key="label", match=models.MatchValue(value=label))])

def ask_qdrant(img):
    vec = embed(img)
    good = client.query_points(COLLECTION, query=vec, limit=K,
                               query_filter=_label_filter("good"),
                               with_payload=True).points
    bad = client.query_points(COLLECTION, query=vec, limit=1,
                              query_filter=_label_filter("bad"),
                              with_payload=True).points
    return {
        "score": 1.0 - float(np.mean([p.score for p in good])),
        "neighbours": [p.payload["path"] for p in good],
        "closest_is_bad": bool(bad) and bad[0].score > good[0].score,
    }

Walkthrough

  • With cosine distance, p.score is the similarity: higher means closer. The anomaly score flips it with 1 − mean, so higher means stranger.
  • The filter restricts the search to label == "good". Without it, enrolled bad samples would count as normal.
  • The second query finds the nearest bad example. If that is closer than any good one, the bag resembles a known fault.
Why a dict? The caller needs a score, reference images and a flag. A dictionary with named keys reads better than a tuple, and adding a field later breaks nothing.
Python: bool(bad) and ... relies on an empty list being falsy: with no bad examples, the expression short-circuits to False and never indexes bad[0]. The float(...) converts a NumPy float into a plain one that serialises cleanly.

look() and grab(): the eyes

_cap = None

def grab(flush: int = 5):
    global _cap
    if _cap is None:
        _cap = cv2.VideoCapture(CAMERA_INDEX)
        time.sleep(1.0)
    for _ in range(flush):
        _cap.read()
    ok, frame = _cap.read()
    if not ok:
        raise RuntimeError("Camera read failed")
    return frame

def look():
    x, y, w, h = ROI
    crop = grab()[y:y + h, x:x + w]
    return Image.fromarray(cv2.cvtColor(crop, cv2.COLOR_BGR2RGB))

Why each piece exists

  • One shared camera object, opened on first use (same lazy pattern as the model).
  • The flush loop. Webcam drivers buffer a few old frames. Reading and discarding them means you embed what is on the tray now. The live preview passes flush=0 to stay fast.
  • read() returns (ok, frame), so a failed read is detected rather than silently giving you None.
  • Slicing. A frame is a NumPy array indexed [row, column], so the y range comes first. Slicing makes a view, not a copy.
  • Colour order. OpenCV uses BGR, while PIL and the model expect RGB. Skip the conversion and everything still “works”, with red and blue swapped.
Why crop at all? A defect that is 2% of the whole tray is 20% of a tight crop. The embedding sees what fills the frame, so crop to the bag.
Python: x, y, w, h = ROI unpacks a tuple into four names, and for _ in range(flush) uses _ to say “I do not need the loop value”.

sort() and arm_command()

def sort(result, threshold):
    verdict = "bad" if (result["score"] > threshold
                        or result["closest_is_bad"]) else "good"
    arm_command(verdict)
    return verdict

def arm_command(cmd):
    if DRY_RUN:
        print(f"   [dry run] arm <- {cmd}")
        return
    with socket.create_connection((PI_HOST, PI_PORT), timeout=90) as s:
        s.sendall((cmd + "\n").encode())
        reply = s.makefile().readline().strip()
    if reply != "DONE":
        raise RuntimeError(f"Arm replied: {reply!r}")

The decision

A bag is bad if its score beats the threshold, or if its nearest neighbour is a known-bad example. Everything else is good. The function returns the verdict so the caller can display it.

The protocol

The laptop opens a TCP connection, sends one line (good, bad or home), and waits for one line back (DONE or ERR ...). The 90 second timeout covers the arm’s slow move.

Why plain sockets, not pymycobot over the network? pymycobot’s API differs between versions, whereas a line of text works with any version and is easy to test with nc. DRY_RUN lets you develop the vision side with no arm attached.
Python: a with block closes the socket even if an exception fires. makefile().readline() wraps the socket as a file so you can read a whole line. {reply!r} in an f-string shows the repr, which makes stray whitespace visible.

The Pi: pi_arm_server.py

POSES = {"home": [...], "above_tray": [...], "tray": [...],
         "above_good": [...], "good": [...], "above_bad": [...], "bad": [...]}

def move(name):
    mc.send_angles(POSES[name], SPEED)
    time.sleep(0.5)
    while mc.is_moving() == 1:
        time.sleep(0.1)

def pick_and_place(dest):            # dest is "good" or "bad"
    grip(False); move("above_tray"); move("tray"); grip(True)
    move("above_tray"); move(f"above_{dest}"); move(dest); grip(False)
    move(f"above_{dest}"); move("home")

How it works

  • Taught poses. Each pose is six joint angles you record by hand-moving the arm and calling mc.get_angles().
  • Waiting. send_angles returns immediately, so move() sleeps briefly and then polls is_moving() until the arm stops.
  • Safe approach. Every pick or drop goes above the target first, then down, then back up, so the gripper never drags across the tray.
  • Server loop. It accepts a connection, reads a line, runs handle(), and replies. Errors are caught and returned as ERR ... so one bad command cannot kill the server.
Why the naming trick? Because poses are named good/above_good and bad/above_bad, one function serves both bins via f"above_{dest}". Adding a third bin means adding two poses, not new code.
Python: SO_REUSEADDR lets you restart the server immediately without “address already in use”. The server has no authentication, so keep it on a trusted network.

The live window and the commands

def wait_for_capture(prompt, status="", colour=(0, 255, 0)) -> bool:
    x, y, w, h = ROI
    while True:
        frame = grab(flush=0)
        cv2.rectangle(frame, (x, y), (x + w, y + h), (0, 255, 0), 2)
        cv2.putText(frame, prompt, (10, 30), cv2.FONT_HERSHEY_SIMPLEX, 0.8, (0, 255, 0), 2)
        cv2.imshow("teabag", frame)
        key = cv2.waitKey(30) & 0xFF
        if key in (13, 32):        # Enter or Space
            return True
        if key in (ord("q"), 27):  # q or Esc
            return False

This function shows the live camera with the ROI box until you press a key, then returns True (capture) or False (quit). Because it returns a boolean, every command is just a loop around it:

while wait_for_capture("Enter to inspect, q to quit", status, colour):
    img = look()
    result = ask_qdrant(img)
    verdict = sort(result, threshold)
    status = f"Last: {verdict.upper()}  score {result['score']:.3f}"

The three commands

  • enroll: capture, add_sample(), repeat. Breaking early keeps what you have.
  • score: capture and print scores without storing anything. With --set-threshold it saves max(scores) × 1.15 to threshold.json.
  • run: the loop above, with the last verdict drawn on the live view.
Python: cv2.waitKey does two jobs: it pumps the window’s events (without it the window freezes) and returns a key code. & 0xFF keeps the low byte, because some platforms add high bits. key in (13, 32) tests membership in a tuple. main() uses argparse sub-parsers so each command has its own options, and if __name__ == "__main__" keeps imports from running the program.

Checklist before trusting results

  • Re-enrol and recalibrate after changing the model, ROI, camera position or lighting.
  • Use diffuse light, and lock white balance and exposure so the camera does not drift.
  • Enrol varied placements and string positions; calibrate on bags you did not enrol.
  • Test with a ladder of faults, from obvious (tape) to subtle (a 2 mm dot), and note where detection stops.
Things that bit this project: the wrong /dev/video index, an auto white balance gone cyan, and localhost resolving to IPv6 (use 127.0.0.1). All three are environment problems rather than model problems.
